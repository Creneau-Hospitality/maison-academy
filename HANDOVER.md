## How it fits together

- **Web app:** one Vite + React + TypeScript app in `src/`, built by Netlify and served at https://maison-academy.netlify.app.
  - `/` is the front page. The staff app replaces it in Phase 2.
  - `/studio` is the content studio: sign-in, card bank, card editor, import, export, people and settings.
- **Database:** Supabase (Postgres) in Frankfurt. The browser talks to it directly with the public key. Every table has row-level security, so the database itself decides who can read or change what.
- **Database set-up** lives in `supabase/migrations/`, run in order in the Supabase SQL editor:
  1. `0001_content_studio.sql`: tables, rules and triggers, tracks, units and settings. Safe to run again.
  2. `0002_seed_cards.sql`: the 189 Phase 0 cards, with their approvals. Generated by `scripts/make_seed.py`. Skips cards that already exist.
  3. `0003_first_admin.sql`: makes David the admin.
  4. `0004_option_order.sql`: option order no longer counts as a content change; shuffles stored options once.
  5. `0005_harder_options_sample.sql`: harder wrong options on 10 cards, sent back to review.
  6. `0006_voids_need_manager.sql`: corrects two cards so voids always need a manager.
  7. `0007` to `0010` `_harder_*.sql`: harder wrong options, by track (generated by `scripts/make_harder_sql.py` from `content/harder/batch*.json`; each only changes live cards whose right answer still matches the Phase 0 export).
  8. `0011_service_steps.sql`: 21 new cards from the 11-step sequence of service (generated by `scripts/make_new_cards_sql.py` from `content/drafts/service-steps-cards.json`).
  9. `0012_checkback_and_bill.sql`: check-back question and bill timing per David's decisions of 20 October.
  10. `0013_selling_cards.sql`: 40 new suggestive selling and upselling cards (generated by `scripts/make_new_cards_sql.py` from `content/drafts/selling-*-cards.json`).
  11. `0014_staff_app.sql`: the staff app's tables, learning engine and rules (see "Staff app" below).
  0001 to 0006 were run on 16 October 2026, 0007 to 0010 on 17 October, 0011 to 0014 on 20 October. (For a restore into an empty database, run 0001 to 0003, then 0004; 0005 only matters if the export predates it.)

### Staff app

- **Where:** the site's front page (`/`) is the staff app; `/studio` is the studio. Staff sessions are stored apart from studio sessions, so a manager can use both on one phone.
- **Login:** `supabase/functions/staff-auth/index.ts`, deployed as the Edge Function `staff-auth` with **Verify JWT turned off** (staff have no login yet when they call it). To redeploy: Supabase > Edge Functions > staff-auth > Code, paste the file, Deploy; then check Settings still shows Verify JWT off. It uses the server keys Supabase provides itself; nothing to set.
  - Activation: a manager issues a single-use code (Studio > Staff), valid 7 days, shown once (only a hash is stored). The person enters it, reads and accepts the privacy notice, chooses a 6-digit PIN. A new code is also how a PIN is reset.
  - Login: staff number + PIN. 5 mistyped PINs pause login for 15 minutes. The reply is the same whether or not the staff number exists. PINs are stored as PBKDF2-SHA256 hashes. A phone stays logged in for 60 days (checked by the database).
- **Learning engine (database functions):** `start_daily_set`, `record_answer` (grades, moves spacing boxes, de-duplicates by the phone's event id, makes private allergen coaching prompts), `finish_set`, `start_readiness`, `my_misses`, `my_progress`, `staff_home`. Studio: `create_staff`, `issue_activation_code`, `list_staff`, `set_staff_active`, `list_venues`. Test accounts: `test_move_date`, `test_reset`. Server only: `svc_*`.
- **Settings** (table `settings`): set size and mix, spacing gaps, allergen box limit, weekly target, venue goal, level thresholds, login limits, code life, privacy notice version.
- **Offline:** the app keeps today's set on the phone and queues answers (`localStorage`), sending them in order when back online. `public/sw.js` caches the app's own files.

### Content rules the database enforces

- Only admins and content reviewers can read cards. Reviewers can only change cards in their own tracks.
- A card can only be live with an approver's name recorded. The name is set by the database, never typed in.
- An allergen card can only go live after a kitchen check, recorded by someone marked as an allergen checker (People screen).
- Reordering a card's options isn't a content change. Staff always see options in a new random order.
- Editing a card's content saves a new version (kept in `card_versions`) and sends it back to review.
- New and imported cards always arrive in review. Cards are retired, never deleted.
- Approvals, retirements, kitchen checks, imports, exports and role changes are written to `audit_log`.
- Tested on 16 October against a local copy of Postgres: 24 checks, all passed.

## Deploy, restore, import

- **Deploy:** push to `main` on GitHub. Netlify builds and publishes within a minute or two.
- **Run locally (developers):** `npm install`, then `npm run dev`. `npm run build` checks the types and builds.
- **Check:** open the site: the front page shows the staff login ("Log in" / "Activate"). Sign in to the studio at `/studio`.
- **Doc-only commits:** add `[skip netlify]` to the commit message so Netlify doesn't spend build credit on them.
- **Export (backup):** studio > Export. "Download cards and versions" gives the full JSON; also take the CSV and settings. Save them to `exports/YYYY-MM-DD-label/` and commit. Do this at the end of each phase and monthly in the pilot.
- **Restore the card bank into an empty database:** run `0001_content_studio.sql` in the Supabase SQL editor. Put the export's `cards.json` at `exports/2026-10-16-phase-0/cards.json` (or point `scripts/make_seed.py` at the new file), run `python3 scripts/make_seed.py`, run the new `0002_seed_cards.sql`, then `0003_first_admin.sql`. Approvals are kept because the SQL editor runs with server rights. (Version history in the export is kept in the file; reloading it into `card_versions` is a later job if ever needed.)
- **Import new cards:** studio > Import, with a JSON or CSV file in the export layout. Imported cards always arrive in review. A card whose ID already exists becomes a new version and goes back to review.
- **Phase releases:** Claude's session can push commits but can't create GitHub releases or push tags. David publishes each release on GitHub (Releases > Draft a new release, new tag `phase-N` on `main`, report pasted as the notes).
